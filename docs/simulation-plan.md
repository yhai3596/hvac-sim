# 空调控制算法仿真平台——规划

目标：搭建一个可复现、可参数化的仿真环境，在不同算法与控制条件下评估设备运行状态（**达温时间、停机时间、循环次数、能耗、舒适度**），用于算法参数调整评估。物理模型采用暖通行业成熟简化模型，保证结论方向性可信；控制算法按 PPT V1.44 复刻，并保留可切换的对照策略。

## 1. 模型架构

```
┌────────────────────────────────────────────────────────────┐
│  仿真引擎 (时间步 Δt = 10s，事件记录)                        │
│                                                            │
│  ┌──────────┐   T_out, Q_solar   ┌──────────────────┐      │
│  │ 天气模型  ├───────────────────►│ 房间热模型 (2R2C) │      │
│  └──────────┘                    └───────┬──────────┘      │
│                                     T_room│  ▲ Q_ac        │
│                                          ▼   │             │
│  ┌────────────────┐  thermo-on/off  ┌────────┴─────────┐   │
│  │ 温控器模型      ├────────────────►│ 变频 DX 设备模型  │   │
│  │ (滞环+最小时序) │                 │ (能力/COP 曲线)   │   │
│  └────────────────┘                 └────────┬─────────┘   │
│                        t1/t2 时序、冷媒侧能力│(含测量偏差)  │
│                                              ▼             │
│                                  ┌───────────────────────┐ │
│                                  │ 控制算法层 (可切换)     │ │
│                                  │ A 定频 on/off 基线     │ │
│                                  │ B 变频固定 Tes         │ │
│                                  │ C V1.44 负荷学习+Tes   │ │
│                                  └───────────┬───────────┘ │
│                                          Tes │             │
│                                              ▼ 设备能力档   │
└────────────────────────────────────────────────────────────┘
```

关键点：**控制算法层只能看到外机可见的信息**——thermo-on/off 时序、室外温度、冷媒侧测得的能力（可注入偏差/噪声）。室温、设定温度、回差对算法不可见，只对温控器模型可见。这样仿真忠实还原"无通讯"约束。

## 2. 子模型与依据

### 2.1 房间热模型：2R2C RC 网络

行业成熟做法（ISO 13790 / EN 52016 简化热网络、ASHRAE 负荷计算的集总参数近似）。两个状态量：室内空气温度 `T_room`、建筑蓄热体温度 `T_mass`：

```
C_air  · dT_room/dt = (T_out − T_room)/R_out + (T_mass − T_room)/R_mass
                      + f_air·(Q_solar + Q_int) − Q_ac,sens
C_mass · dT_mass/dt = (T_room − T_mass)/R_mass + (1−f_air)·(Q_solar + Q_int)
```

- `1/R_out = UA`：围护结构综合传热（含渗透风），默认 350 W/K（北美轻质木结构独栋 150~200 m² 量级）；
- `C_air`：空气+轻质内饰热容，默认 3.0 MJ/K；`C_mass`：蓄热体热容，默认 40 MJ/K，`R_mass` 默认 1/500 K/W；
- `Q_solar`：白天正弦包络（峰值默认 2.5 kW，可调），`Q_int` 内扰恒值 300 W；
- 潜热在第一版按显热比 SHR 折入能力（默认 0.75），不单独建湿度状态（V1.44 也未用湿度）。

### 2.2 天气模型

`T_out(t) = T_mean + A·sin(2π(t − t_peak)/24h)`，默认 T_mean=30℃、A=5℃、峰值 15:00；支持恒温工况与多天序列。日照与 T_out 相位耦合。

### 2.3 变频 DX 设备模型

参照 EnergyPlus DX coil / AHRI 210/240 的性能曲线思路，取一阶线性化（系数可调）：

```
Q_avail = Q_rated · [1 + kQ_oat·(35 − T_out)] · [1 + kQ_te·(Tes − Tes_nom)]
COP     = COP_rated · [1 + kE_oat·(35 − T_out)] · [1 + kE_te·(Tes − Tes_nom)]
```

- 默认 Q_rated = 7.0 kW（2 冷吨级）、COP_rated = 3.3 @ (35℃, Tes_nom=7℃)；
- `kQ_oat ≈ +1%/℃`（室外温度每降 1℃ 能力增约 1%）、`kE_oat ≈ +2%/℃`；
- **Tes 敏感度（核心机制）**：`kQ_te ≈ −4%/℃`（Tes 抬高 → 能力下降）、`kE_te ≈ +2.8%/℃`（Tes 抬高 → COP 上升），与"蒸发温度 +1℃ ≈ COP +2~3%"的行业经验一致；
- 启动动态：能力一阶惯性上升（时间常数 60s），复现启动损失；停机即 0；
- 定频基线机（算法 A）：同 Q_rated 但无 Tes 调节、COP 取 3.0（SEER 13 级），启停无级间调节；
- **能力测量通道**：算法层拿到的是 `Q_meas = Q_true · (1 + bias) + noise`，bias/noise 可调，用于研究 Gr×Δh 误差的影响。

### 2.4 温控器模型（北美替代场景的关键外部件）

- 滞环控制：`T_room ≥ T_set + db/2 → thermo-on`；`T_room ≤ T_set − db/2 → thermo-off`；
- 回差 db 默认 1.0°F（0.56℃），可调 0.5~2°F，模拟跨品牌差异；
- 采样周期 60s（典型数字温控器）；最小开机 3min / 最小停机 5min（压缩机保护，多数温控器内置）；
- 对算法层完全黑盒。

### 2.5 控制算法层

| 策略 | 说明 |
| --- | --- |
| A 定频 on/off | 被替代对象基线：thermo-on 即满能力，thermo-off 即停。 |
| B 变频固定 Tes | 变频机不学习：Tes 恒为 Tes_nom（或手动设定值）。 |
| C V1.44 复刻 | 循环定义、有效性判据（t1/t2 窗口、保护）、外温 16 分箱 × 昼/夜、7 天采样中心值法 + 70% 信赖区间、新样本替换规则、目标总负荷（STEP1~3）、每 20s 能力恒定外推预测（STEP4）、120/110/90/80 滞环 UP/DOWN、Tes 分箱保存与步进调整（步长/上下限可调）。 |

算法 C 的可调参数（对应评估需求）：TA 目标运转时间（默认 60min）、判定死区（默认 ±20%）、滞环宽度（默认 10%）、Tes 步长（默认 0.5℃）、Tes 范围（默认 4~14℃）、学习期样本门槛、"预学习完成"开关（跳过 7 天冷启动直接给定 q 初值，便于研究稳态行为）。

### 2.6 评估指标

每次运行输出：

- **达温时间**：初始 pull-down 时间（仿真开始/设定阶跃 → 首次达温）；每循环 t2（thermo-on → thermo-off）分布；
- **停机时间**：每循环 t1 分布；
- 循环次数/天（压缩机启停次数）；
- 日耗电量 kWh、平均 COP、启动损失占比；
- 舒适度：室温对设定的均方根偏差、超出 [T_set−db, T_set+db] 之外的时间占比、最大超调；
- 算法内部状态轨迹：各箱 q 收敛过程、Tes 轨迹、UP/DOWN 信号事件。

### 2.7 验证场景

| 场景 | 配置 | 验证点 |
| --- | --- | --- |
| S1 设计日稳态 | 恒定 35℃、预学习完成 | 稳态循环合理性；A/B/C 指标对比 |
| S2 典型夏周 | 30±5℃ 正弦 × 7 天、冷启动学习 | q 收敛过程、学习期 vs 学成后指标 |
| S3 轻负荷季 | 24±4℃ | 长循环丢样本问题复现（缺点 2.2-8） |
| S4 设定阶跃 | 稳态后 T_set 从 25.5→24℃ | pull-down 变慢问题复现（缺点 2.2-6） |
| S5 参数扫描 | TA ∈ {30,45,60,90}min、db ∈ {0.5,1,2}°F、测量 bias ∈ {−15%,0,+15%} | 参数敏感度、鲁棒性 |

## 4. 已知简化与边界

1. 2R2C 单区模型不含多房间气流分配、湿度状态（SHR 折算）；结论用于**算法相对比较与参数趋势**，不用于标称能效值申报；
2. 设备曲线为线性化近似，系数可按机型实测替换；
3. 化霜、LP/HP 保护在制冷仿真中默认关闭（V1.44 相应无效判据保留接口）；制热模式结构对称，第一版聚焦制冷；
4. 温控器不建 anticipator/智能预测行为，用回差扫描近似覆盖其影响。

# v2 增量（气候地点 / 湿度 / 压缩机 / 制热 / 方案对比）

针对两项客户反馈（达温慢、除湿不足）与地点化评估需求，模型升级如下：

## A. 气候地点模块（`sim/climate.py`）
- 8 个代表站：洛杉矶/弗雷斯诺/休斯顿/达拉斯/迈阿密/奥兰多/波士顿/纽约；
- 每站内置 ASHRAE 设计工况：0.4% 夏季设计干球、日较差、MCWB、典型露点、99.6% 冬季设计干球（文件顶部注明来源与复核要求，网络受限未能在线核对 ashrae-meteo.info）；
- 场景：夏季设计日 / 典型夏日 / 冬季设计日 / 典型冬日（峰值+日较差余弦轮廓 = ASHRAE 设计日方法简化；露点按日恒定）。

## B. 房间湿平衡
- 单区含湿量状态：渗透湿负荷（ACH×室外露点）+ 内扰产湿 − 盘管除湿 + 盘管存水再蒸发；湿容量放大 ×15（家具缓冲）；
- 输出 RH%、除湿量 L/天、RH>60% 时间占比。

## C. 设备模型升级（`sim/models.py` Device）
- **显式压缩机频率状态**：启动频率(默认30Hz)+低频保持(回油180s)+斜率受限积分控制追踪 Te→Tes（制热 Tc→Tcs）；由此"压缩机到最大输出时间"成为可测指标；
- **风量**：CFM/ton 为跨品牌匹配变量（影响能力 capFF、盘管温差、旁通因子）；网页端另有"配套内机模式"（风量随频率联动 300→460）；停机风机策略 AUTO/常开（常开把盘管存水再蒸发回房间）；
- **潜显拆分**：ADP/旁通因子法（ADP=Te+2℃；BF 随风量变化）。注意其推论：变频定 Te 控制下 SHR 由 Tes 决定、与风量近乎解耦——正是 V1.44 抬 Tes 牺牲除湿的机理；
- **制热**：热泵能力/COP 随外温衰减、化霜（湿冷区累计运转触发、化霜期能力 0 与 PPT 一致）、8kW 电辅热（两级温控逻辑）。

## D. 算法层（`sim/algorithms.py`）
- V1.44 双模式：制冷 Tes（能力UP=Tes↓）/制热 Tcs（能力UP=Tcs↑），制热分箱 −20~22℃（PPT 幻灯 8）；
- 所有 V1.44 变量可调：TA、判定死区/滞环、目标值调整速率、每循环限幅、有效循环窗口、预学习初值。

## E. 指标扩展（`sim/simulator.py`）
达温间隔（循环周期）、压缩机到峰值95%时间（高水位标记法）、RH 统计、净除湿量、化霜次数、辅热耗电。

## F. 基准点方案对比工作流（网页端）
设参数 →「重置统计」→ 运行 →「记录当前运行为方案」→ 改参再跑再记录 → 与基准并排 Δ% 对比（首条记录自动为基准，可改）；CSV 复制导出；localStorage 持久化。

# v3 增量（负荷满足度 / 能力段 / 内机风量三模式）

## G. 负荷满足度（选型锚定）
- 变量：满足度 = 额定能力 ÷ 建筑设计负荷，范围 50~150%，默认 100%；
- 机制：按当前模式（制冷用显热+潜热设计负荷、制热用制热设计负荷）把所有负荷源
  （UA/ACH/日照/内扰显热/产湿）等比缩放使满足度精确成立；房屋参数保留，
  决定负荷构成与热惯性，满足度决定负荷总量；热容不缩放。

## H. 能力段
- 两档可选：3 Ton（10.55 kW）/ 5 Ton（17.59 kW）；制热额定 = 制冷 ×1.09；
  内机总风量 = CFM/ton 基准 × 吨位 × 当前风量比例。

## I. 内机风量三模式（产品定义）
| 模式 | 逻辑 | 可调参数 |
| --- | --- | --- |
| 固定风挡 | 100% 风量输出 | — |
| 两档风 | 1 档 70% / 2 档 100%（档位选择） | 档位 |
| 自动风 | 达温停机后再次启动按初始风量（默认 60%）；保持时长（默认 50min）内未收到达温停机信号，则每隔提档间隔（默认 10min）提高一档（默认 +10%）直到 100%；外机按自身逻辑运行 | 初始风量、保持时长、提档间隔、每档步进 |
- 风量比例作用于：能力修正 capFF、盘管温差（Te/Tc）、旁通因子（除湿）、
  风机功率（风机定律 ∝ 风量³）；
- 新增验证场景 V9：三模式对比 + 自动风保持时长/初始风量扫描（迈阿密设计日）。

# v5 增量（湿源变量细化 / 满足度缩放修正）

## L. 湿源三路独立变量（单位各自物理，不折算成比例）
| 湿源 | 变量与单位 | 计算 |
| --- | --- | --- |

## M. 满足度缩放修正
满足度（额定能力/总设计负荷）含义不变，但缩放**只作用于显热源**（UA/日照/内扰显热）：
缩放系数 = (额定能力/满足度 − 设计潜热) / 设计显热（制热支路扣除新风显热后缩放围护部分）。
湿源（ACH/新风/产湿）一律保持滑杆物理面值——避免"负荷缩放"把湿量变成无物理意义的比例。

## N. 验证

产湿扫描（0.3/1.0/2.0 kg/h：RH 均值 63.7%→70.1%）；17 项单元测试；JS/Python 交叉验证
（vent=200、mgain=1.2 工况逐项一致）。

# v6 增量（智能实验助手：自然语言 → 评估 → 批量仿真 → 报告）

## O. 交互流程（两阶段：先评估，再执行）
输入自然语言测试需求 → **解析为实验计划并给出规模评估**（方案数 / 每方案时长 / 合计机时 /
按实测步率推算的预计耗时）→ 用户确认（可直接编辑计划 JSON）→ 逐方案批量仿真 → 自动记入
方案对比表 → 对比矩阵 + LLM 分析报告。解析与执行分开，避免一句话直接触发几十分钟的运算。

## P. 计划结构：主对比 × 条件维度（逐一调节，不做全交叉）
```json
{"days": 2, "warmup_h": 6,
 "base":       {"所有方案共同的设定": "只写与默认值不同的键"},
 "compare":    [{"name": "自动风", "set": {"fanCtrl": "auto"}},
                {"name": "两档风·2档", "set": {"fanCtrl": "two", "twoStage": 2}}],
 "conditions": [{"name": "基线", "set": {}},
                {"name": "高负荷·满足度70%", "set": {"sat": 70}}],
 "focus":      "用户关注的对比点"}
```
实际方案 = `compare` × `conditions`，共 |compare|×|conditions| 个：**同一条件下的各臂之间只差
一个变量**（受控对比），**每个条件档相对基线也只改一个变量**（逐一调节）。条件维度之间不相乘
——「热负荷 × 湿度 × 设定温度 × 地区」是 1+2+2+2+2=9 个条件档而非 16 种组合。
- 未提及的变量一律取出厂默认值（页面加载时的 `P0` 快照）；
- 校验层持有全部 34 个可设变量的白名单（类型/范围/枚举），非法键丢弃、越界截取并逐条警告；
- 单变量审计：臂间或条件档内改动超过一个"根变量"时给出警告（`fanCtrl`+`twoStage`、
  `algo`+其参数、`ins`+UA/ACH 视为同一物理选择，不算多变量）；
- 与共同设定等价的条件档、重复档自动去除。

## Q. 三条解析路径（LLM 为主路径）

自然语言的写法是无穷的，正则永远追不上——两轮多 agent 对抗审计已经证明了这一点。因此
**LLM 按平台接口契约编译计划是主路径**，内置正则只是无 API 时的降级兜底（页面会明示）。
主路径的正确性取决于两件事，两件都要被验证：给模型的**接口契约**够不够精确，模型的输出
能不能被平台**直接执行**。

### Q0. 给模型的接口契约（`buildParsePrompt`，全部由 `VAR_DEFS` 单一数据源生成）
1. **可设变量表**：31 个键名 + 类型 + 取值范围/枚举 + 默认值 + 说明；
2. **输出结构**：days / warmup_h / base / compare / conditions / focus / **notes**；
3. **硬性规则 12 条**，其中几条是从审计缺陷里反推出来的护栏：只能用表里的键名（平台没有的
   变量要写进 notes 而不是编造键名）、臂间只差一个变量、条件档不交叉相乘、越界取最近合法值
   并在 notes 说明、tgtb 随模式区分 Tes(4~14)/Tcs(38~52)、**fixed 与 two+twoStage=2 物理
   等价不可排成两臂**、"档"多数是量词、陈述性前提进 base 而追加语气进 conditions；
4. **指标词表**：让 focus 与平台实际输出的指标对齐；
5. **两个完整示例**：多维对比、带明确数值与地点的制热对比。

`notes` 是新增的**模型回报通道**：模型把"我替你选了什么、哪里不确定、哪个需求平台覆盖不了"
写回来，校验后并入计划预览的"已自动取值"一栏——避免模型静默臆测。

## Q1. 三条解析路径（按优先级）
1. **粘贴 JSON 直跑**：输入本身是计划 JSON（可带代码围栏）→ 跳过解析直接校验评估；
2. **LLM 解析**：变量目录（键名/含义/范围/默认值，由 `VAR_DEFS` 自动生成）+ 计划结构 + 分组
   规则组装为「实验计划编译器」提示词，走既有多 API 轮询（失败自动切换）；
3. **内置规则解析**（无 API 回退）。这一路经过两轮多 agent 对抗审计（6 类用户画像各出 12 条
   真实口语语料，共 72 条 → 逐条跑真解析器判定 → 复核 105 条候选缺陷、确认 16 条），据其
   结论重写；每条缺陷语料都已固化进 `check_parse.js`（60 条断言）：
   - **主对比轴**（15 条）：风量模式、控制算法 A/B/C、预学习开关、停机风机策略、电辅热、
     能力段、负荷满足度、Tes/Tcs 目标、设定温度、地点、基准风量、温控器回差、UP/DOWN 死区、
     TA、能力测量偏差、季节工况。选取规则：**优先取"控制/设计"类轴**（用户能改的产品选择），
     地区与季节属工况，只在没有控制类轴可比时才充当对比臂；同类中取句中出现最早者；
     其余命中的轴降级为条件维度，**只点名一次的轴并入共同设定**（如「同样 3T 的机器装 LA 和
     休斯顿」→ tons 进 base、loc 作对比）；
   - **条件维度库**（15 条）：热负荷/选型裕度、湿度负荷、设定温度、地区气候、季节工况、
     围护保温、房屋规模、气密性、能力段、基准风量、回差、UP/DOWN 死区、能力测量偏差、
     电辅热、停机风机、预学习；用户说「不同 X」但没给数值时取代表档位并标注为"已自动取值"；
   - **口语与写法容错**：中英地名及州名别名（LA/NYC/Houston/加州/德州…，英文词边界+大小写
     不敏感）、算法反序写法（「C算法跟B比」）、「定频机 vs 变频机」、「风量那三种模式」、
     「风量大一点小一点」、「小一号/大一号」「带不动」「负荷大」、「保温好差都试试」、
     「设到 26 度跟 23 度比」；
   - **枚举数值抽取**：`nearNums` 支持「满足度 70% 和 130%」「Tes 7℃ 和 12℃」「cfm 350/450」
     这类关键词后跟一串值的写法；弱动词（设到/调到/开到）必须带温度单位，避免抢走
     「TA 调到 90」「新风开到 200」里别的变量的数字；
   - **只给一个值时与默认值配成两臂**：「死区放宽到 30% 看一下」→ 默认 20% vs 30%，
     而不是无对照地跑一版；
   - **越界值告警而非静默丢弃**：「TA 打 8、10、12」→ 提示超出 20~120 min 并请确认单位；
   - **天气对照识别**：「分设计日和普通热天两种天气」「再碰上最冷那几天」→ base 用典型日、
     设计日单列为条件档，而不是整轮都跑极端日；
   - **物理等价臂检测**：固定 100% 与两档风 2 档在本模型中都是 100% 风量，同时出现时自动把
     两档风臂改为 1 档（70%）并告警——否则报告会拿两条必然重合的曲线得出"二档多余"的假结论；
   - **不再有"无法解析"死路**：完全无法识别时给出默认三风量模式对比 + 明确警告；解析出的
     计划若只有 1 个方案（无对照）也会明确告警。

   第二轮审计修掉的都是"看起来正常、结论却错"的静默缺陷，值得单列：
   - **量词「档」被误判为风量模式**：「UA 大一档小一档」「回差 2°F 带一档」曾让 base 里
     出现 `fanCtrl:two, twoStage:1`，给全部方案偷偷锁上 70% 风量（会同时扭曲制热与除湿
     结论），界面上还宣称"这是你点名的共同设定"。现要求风量语境，并在列举风量模式时才
     接受裸「N 档」。
   - **数值符号被吞**：`bias −10%` 被读成 `+10%`，弱机与强机的结论方向直接反转。现仅对
     可取负的变量解析符号（避免把「10-20」读成 10 与 −20）。
   - **单位分支顺序**：`NUM_UNIT` 里单字母 `h` 排在 `Hz` 前且大小写不敏感，「50Hz跟放到
     70Hz」只匹配到 `50H` 就截断，第二个值永远抓不到。单字母单位已移到分支末尾。
   - **枚举连接词只列了几个**：「3kw跟5kw」「从10改成20」「0.3拉到0.6」在第一个连接词处
     断掉，只剩首值——而首值若恰等于默认值还会被去重删掉，整条对比作废。现支持连续多个
     连接词，且显式值即使等于默认值也会写进基线名（「基线（产湿0.3kg/h）」）。
   - **越界值静默丢弃**：`TA 8/10/12` 中越界的 8 被丢掉且无提示。现一律告警；对 TA/死区
     这类轴若有效值不足两个则钳位保留并提示"多个臂可能因此参数相同"。
   - **追加档被当成全局设定**：「顺便把保温差的房子也来一版」曾改掉 `base.ins`，让全部方案
     都跑烂保温房。现区分追加语气（→ 增量条件档，基线保持默认）与限定语气（→ 共同设定）。
   - **伴随参数跨臂污染**：算法 B 的目标温度会残留到 algo=C 的臂上。展开 variants 时改为
     按"根变量"整组覆盖；算法轴与目标温度同时出现时，B 直接展开成每个目标一个臂。
   - **裸词误命中**：「我想看看湿度到底能压到多少」里的"湿度"是输出指标，曾被当成湿源维度
     凭空加两档、方案数从 3 涨到 9。湿度维度改为要求"湿度负荷/各种潮/新风/产湿"等明确措辞。
   - **用户明写的值被忽略**：「预热2小时」曾被硬编码的 24h 静默放大 12 倍。现读取用户值。
   - 另补齐 fmax/qint/rate 等此前在轴与维度里完全缺席的变量，以及英文季节词（winter design
     day）、能力衰减口径（衰减 20%/40% → 满足度 80%/60%）、方案数自检（"仨方案"对不上会告警）。

## R. 批量运行器
- 暂停主循环 → 快照当前参数；每个 variant：默认值 + base + set（loc/scen 先行以重算气候与
  模式默认值，ins 展开为 UA+ACH，再覆盖显式键）→ 预热 → **只清统计、保留算法学习状态**
  （`resetStats(true)`）→ 测量 → `makeRecord`；
- **默认预热 24 h（整日）+ 测量 3 天**，依据见验证报告 3b 节：湿平衡时间常数 ≈25 h，预热
  不足会系统性高估除湿量；预热若不保留学习器，等于测量段从零重学；V1.44 的 Tes 学习有
  双稳态，故所有方案共享同一预热时长与同一测量起始时刻，计划评估阶段对 <24 h 预热告警；
- 分块执行（3000 步/块）并让出事件循环：进度条推进、图表实时重绘、**按实测步率显示剩余时间**，
  可随时「停止实验」；
- 结束（含中止）后恢复运行前参数与运行状态；结果以 `AI·` 前缀入方案对比表，首个设为基准。

## S. 结果输出
- **对比矩阵**（无 API 也有）：行 = 条件档，列 = 关注指标（由 focus 关键词选取：达温→t2/到峰值、
  除湿→除湿量/RH>60%、舒适→t2/RMSE/出带%/RH>60%、能耗→kWh…），单元格为
  「基准臂值 → 对比臂值（相对变化）」并按"该指标是否向好"着色——直接回答"不同条件下两种
  方案的差异如何变化"；无对比臂时退化为逐方案差异清单；
- **LLM 报告**：复用既有报告管线，提示词额外携带 `focus` 与舒适度指标映射
  （达温 t2/初始达温=速度，RMSE/出带%=温度稳定，RH/RH>60%=湿度舒适）；
- 计划来源（粘贴 JSON / 某 API 解析 / 内置规则）、自动取值项、校验警告在评估阶段全部明示。

## T1. LLM 主路径的评测（`eval/`）

`eval/run_eval.js` 对每条语料取出页面 `buildParsePrompt()` 生成的**真实提示词**发给模型，
把返回的 JSON 喂回页面的 `validatePlan()`，按七个维度打分，并可选 `--execute` 把计划真的
送进 `runExperiment` 跑一遍：

| 维度 | 判定 |
| --- | --- |
| JSON 结构合法 | 能解析且含 compare/conditions |
| 键名合法 | 校验层未报"忽略未知变量" |
| 取值在范围内 | 校验层未报越界截取 |
| 单变量纪律 | 臂间、条件档内只改一个根变量 |
| 物理有效性 | 无等价/重复臂（平台一旦出手修复即判模型失败） |
| 规模合理 | 方案数在上限内 |
| 语义覆盖 | 用户点名的对比对象/维度/数值都在计划里 |

语料 24 条，全部取自真实工程师口语，多数是曾把正则解析器打挂的句子；断言写的是"编译结果"
而非实现细节，因此可用于横向比较不同模型。

**反向对照是这套评测的关键**：`responses-bad.json` 注入 10 种真实 LLM 失败模式（编造键名、
越界、一臂改两变量、排出物理等价臂、制热 Tcs 用在制冷、条件全交叉致方案爆炸、返回散文、
忽略用户明写的预热、把输出指标当条件维度、量词误判）。评分器在这 10 条上给出**全部通过
0/10**，证明它抓得住错——一个只会打满分的评分器没有价值。

这套评测在开发中已经发现并修掉一个真实缺陷：**等价臂防护此前只写在 `ruleParse` 里，
`validatePlan` 没有**，也就是说用户指定的主路径（LLM）恰恰缺这层保护。现已移到
`validatePlan`，覆盖 LLM / 粘贴 JSON / 正则三条入口。

当前基线（**适用范围务必看清**）：`eval/responses.json` 的模型回复是 Claude 在开发会话内
充当被测模型产生的，不是对真实 API 的实测（开发环境无外网出口）。24/24 且可执行 24/24
只能证明"契约可表达 + 脚手架有效 + 链路可执行"三件事，**不能说明任何真实模型的水平**——
期望值与模型回答出自同一方。真实分数需用 `--base/--key` 自行跑。

# AI 辅助部署提示词

把下面「提示词正文」整段复制给协助部署的 AI（新会话）。它把这个项目部署过程中真实踩过的坑
写成了硬规则——目的是让同样的问题不再重复出现一遍。

配套：人看的流程在 [`runbook-deploy.md`](runbook-deploy.md)，脚本在 `deploy/`。

---

## 提示词正文

> 你要协助我把一个纯静态站点（空调控制算法仿真平台）部署到一台 Linux 服务器上。
> 仓库：`https://github.com/yhai3596/hvac-sim`，部署脚本在 `deploy/install.sh`（幂等，可反复跑）。
>
> **你没有服务器的 shell。** 所有命令由我在服务器上执行、把输出贴回给你。你的职责是：
> 给出一次一步的命令、读我贴回的输出、定位问题、给下一步。不要假装已经执行过，
> 不要在我贴回结果之前就宣布成功。
>
> ### 第一步（不要跳过）
>
> 让我先跑环境探测，再决定任何事：
>
> ```bash
> bash deploy/preflight.sh 我的域名
> ```
>
> 拿不到仓库时用：
> `curl -fL -o /tmp/p.sh https://raw.githubusercontent.com/yhai3596/hvac-sim/<分支>/deploy/preflight.sh && bash /tmp/p.sh 我的域名`
>
> 在看到探测结果之前，**不要**让我执行任何会改动系统的命令。
>
> ### 硬规则
>
> 1. **不要跟已有服务抢端口。** 80/443 被 Caddy/nginx/Apache 占着时，正确做法是把站点并入
>    那个服务，不是杀掉它、也不是让新服务去 bind。那多半是别人的生产站点。
> 2. **改别人的配置前先备份，校验失败立刻还原。** 顺序恒为：备份 → 改 → 校验（`caddy validate`
>    / `nginx -t`）→ 通过才 reload。任一步失败就把备份 `cp -a` 回去再报告，绝不留下改坏的配置。
> 3. **验证要用"只有成功才会出现"的证据。** 反例（这次真的中招了）：用 `caddy adapt | grep 域名`
>    判断站点是否生效——域名可能来自用户原有的站点块，于是误判为"已生效"。正确做法是 grep
>    只有新配置才会出现的字符串，比如站点根目录 `/opt/hvac-sim/dist`。
> 4. **"服务起来了"不等于"部署成功了"。** 必须确认返回的是本项目的页面：
>    `curl -sS https://域名/ | grep -c '空调控制算法'` 要 ≥1。默认欢迎页会完美地伪装成成功。
> 5. **不要关闭 TLS 校验、不要 `-k`、不要改 hosts 绕过问题。** 连不上就换取码路径。
> 6. **不确定就先探测再动手**，不要凭猜测改配置。一次给一条命令，等结果。
> 7. 云控制台的安全组你我都改不了，需要放行 80/443 时明确提示我去点。
>
> ### 三个决策点（用探测结果回答，不要问我）
>
> - **代码怎么上服务器**：`github.com` 通 → git clone；只有 `codeload.github.com` 通 → 拉源码包；
>   都不通 → 我在本地打包 scp 过去，然后用 `SRC_DIR=` 离线安装。只有 git 那条支持自动更新 timer。
> - **用哪个 web 服务器**：80/443 空闲 → nginx + certbot；被 Caddy 占 → 并入 Caddy（不装 certbot，
>   证书 Caddy 自动签）；被别的占 → 停下来问我。
> - **证书**：nginx 走 certbot；Caddy 自己管。DNS 没生效就先 `SKIP_TLS=1` 跑 HTTP，之后重跑补签。
>
> ### 已知坑（出现即照此处理，不要重新摸索）
>
> | 现象 | 处理 |
> | --- | --- |
> | `git clone` 报 `GnuTLS recv error (-110)` / 连接重置 | GitHub 被墙，换 codeload 源码包或离线 `SRC_DIR=` |
> | `curl` 拉文件长时间无输出 | `raw.githubusercontent.com` 不通；`-fsSL` 的 `-s` 吞掉了错误，去掉 `-s` 加 `-m 120` |
> | `bind() to 0.0.0.0:80 failed (98)` | 端口被占，见硬规则 1 |
> | 站点打开是 Caddy/nginx 默认欢迎页 | ① 域名可能已写在别人的站点块地址列表里，要先摘出来；② 站点块只写域名时 HTTP 侧会被 `:80` 兜底块截胡，需显式写 `http://域名 { redir https://{host}{uri} }` |
> | 非交互执行卡死 | `sudo` 在要密码，先 `sudo -n true` 验证 |
> | 部署成功但外网打不开 | 安全组没放行；先让我在服务器上 `curl -I http://127.0.0.1/` 区分是本机问题还是网络问题 |
>
> ### 完成标准
>
> 下面四条全过才算完成，请让我逐条执行并把输出贴给你：
>
> ```bash
> curl -sSI https://域名/ | head -3                      # 有 200
> curl -sS https://域名/ | grep -c '空调控制算法'         # ≥1，证明是本项目页面
> curl -sSI https://域名/ | grep -i content-type          # 带 charset
> curl -sSI http://域名/ | head -3                        # 301/308 跳 HTTPS
> ```
>
> 全过之后，用一段话告诉我：站点地址、代码放在哪、怎么更新、以及哪些事情还需要我自己做
> （比如安全组、证书续期是否自动、自动更新是否可用）。

## 为什么是这些规则

每一条都对应一次真实的返工：

| 规则 | 起因 |
| --- | --- |
| 先探测再动手 | 前三轮往返全都是在盲猜服务器上有什么，探测脚本 30 秒就能回答 |
| 不抢端口 | nginx 反复 `bind() failed`，因为机器上跑着 Caddy 和 7 个别的站点 |
| 验证用唯一证据 | `grep 域名` 匹配到了用户原有的站点块，脚本据此认为"无需改动"，结果站点文件从未被加载 |
| 服务起来≠部署成功 | 服务正常、校验通过、日志无错，页面却是 Caddy 欢迎页 |
| 改配置先备份后校验 | 主 Caddyfile 上跑着 7 个生产域名，改坏了是事故 |
| 去掉 `curl -s` | 一条卡住的命令看不出任何症状，白白浪费一轮 |
